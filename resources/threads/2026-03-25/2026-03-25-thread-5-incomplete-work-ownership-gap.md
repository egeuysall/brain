# Thread 5 - Incomplete work marked done

## Quick Actions

- Source thread: [Open post](https://www.reddit.com/r/ExperiencedDevs/comments/1kg7vgf/how_do_you_deal_with_devs_who_dont_take_ownership/)
- Local index: [Back to top 10](./2026-03-25-top-10-outreach-posts.md)

## Snapshot

- Role signal: Lead engineer managing senior dev quality issues
- Situation type: Work declared complete without meeting standards
- Tool/context signal: PR feedback loops failing to enforce quality

## Pain Summary

The lead repeatedly sees incomplete, untested work passed as done despite prior feedback and formal reviews, creating constant rework and trust erosion.

## Why This Is High-Signal

- Explicit ownership and delivery-quality breakdown.
- Shows where “done” status diverges from actual readiness.
- Indicates operational risk from weak closure criteria.

## Suggested Public Reply (Copy)

```text
This is less a people problem and more a system-definition problem: if incomplete work can be marked done, your team has no enforced definition of done. Once “done” and “ready” diverge, quality debt and ownership conflict become daily operating cost.
```

## Suggested DM Idea (Copy)

```text
You’re dealing with the exact gap many leads hit: feedback exists, but closure standards are still optional in practice. If useful, I can share a compact DoD/PR gate pattern that makes ownership visible and prevents “untested done” loops.
```

## Personalization Notes

- Reflect their lead responsibility pressure.
- Avoid blaming individual contributors.
- Center on system and standards enforcement.
